# Эксплуатация и восстановление

## Российский VPS, один узел

Практическая стартовая конфигурация для небольшой нагрузки: Linux, 1–2 CPU, 2 ГБ RAM, SSD, Docker Compose v2, домен с A/AAAA на сервер. Во время сборки Node требуется дополнительная память; на маленьком сервере соберите образ заранее. Порты 80/443 открыты, API напрямую наружу не публикуется.

```sh
cp .env.example .env
# В .env настроить APP_DOMAIN и совпадающий ALLOWED_ORIGINS.
# DEMO_MODE=false, COOKIE_SECURE=true. DATABASE_URL можно оставить пустым для SQLite.
docker compose up -d --build
docker compose exec api python -m app.admin operator@example.ru --name 'Оператор'
```

Пароль вводится скрыто; предустановленных production-паролей нет. SQLite хранится в именованном томе `edin_orders_data`. Не выполнять `docker compose down -v`, если нужно сохранить данные. Без `-v` остановка/пересоздание контейнеров сохраняет тома.

Caddy выдаёт и продлевает HTTPS-сертификат автоматически при корректном DNS и доступности ACME. JS, CSS, шрифты, иллюстрации, Swagger обслуживаются с вашего сервера. Образ можно собрать заранее, сохранить `docker save` и загрузить в закрытой сети. Работающая система с SQLite не обращается к npm/PyPI/Google/зарубежной БД.

Ограничение: один узел SQLite. Горизонтальное масштабирование с общим SQLite-файлом не поддерживается; для нескольких экземпляров используйте PostgreSQL.

## Автовосстановление

- Docker `restart: unless-stopped` перезапускает завершившийся контейнер.
- Внутренний supervisor проверяет health; после трёх неудач завершает зависший процесс, чтобы restart policy могла его восстановить.
- API проверяет JWT/роль и бизнес-правила после каждого рестарта, состояние хранится в БД.
- SSE переподключается с курсором, плюс polling каждые 30 секунд.
- Caddy сертификаты и данные базы находятся в томах, отдельно от образа.
- Автообновления произвольных новых версий зависимостей не включены: обновление сначала проверяют тестами и резервной копией.

Автоматика не чинит закончившееся место на диске, потерю VPS/аккаунта, изменённый тариф или сетевую блокировку. Для реальной эксплуатации нужен периодический контроль квот, диска, сертификата и резервирования. Обещание «навсегда без вмешательства» для интернет-сервиса было бы недостоверным.

## Журналы и контроль

```sh
docker compose ps
docker compose logs --tail 100 api
docker compose logs --tail 30 backup
curl --fail https://orders.example.ru/api/v1/health
```

Запросы логируются со временем, методом, путём, HTTP-кодом и `request_id`; токены/пароли/тела не логируются. На VPS Docker ротация — 3 × 10 МБ на сервис. В Render действуют его сроки хранения журналов. Ошибки БД получают 503, внутренние ошибки 500; пользователю не возвращается traceback.

## Резервные копии SQLite

Compose-сервис `backup` создаёт согласованную копию через SQLite Online Backup API раз в 6 часов. Архив содержит БД и локальный JWT-ключ. Есть integrity_check, SHA-256, права 0600; срок хранения 30 дней, минимум 7 копий. При стандартном сценарии RPO до 6 часов; RTO определяется скоростью развёртывания/размером БД и не измерен как SLA.

```sh
docker compose exec api python -m app.maintenance --directory /tmp/manual-backup
# Для штатной копии используйте существующий backup-сервис с томом /backups:
docker compose run --rm backup python -m app.maintenance --directory /backups
```

Том резервных копий на том же VPS защищает от ошибки приложения/обновления, но не от утраты сервера. Настройте перенос архивов на независимое российское хранилище. Архивы содержат персональные данные и хеши: закрытый доступ и шифрование вне сервера обязательны для реального использования.

Восстановление — управляемая операция владельца: остановить api/backup, сохранить текущий том отдельной копией, проверить SHA-256 выбранного архива, извлечь **только** `orders.sqlite3` и `.jwt-secret` в том с владельцем UID 10001, не оставлять старые `orders.sqlite3-wal`/`-shm`, затем запустить сервисы и проверить заказы/вход. Не распаковывайте неизвестные архивы. Потеря локального JWT-ключа завершит действующие сессии; заказы сохранятся.

## PostgreSQL / Render

Compose backup предназначен для SQLite. Для PostgreSQL используйте `pg_dump` или управляемые backup/PITR вашего провайдера. Если в Compose задан `DATABASE_URL`, выключите SQLite backup-сервис и настройте отдельный процесс PostgreSQL-резервирования. На Render Free нет постоянного диска и бесплатных фоновых задач: локальный backup внутри веб-контейнера не считается резервной копией.

Пример с переменной, предварительно введённой через менеджер секретов:

```sh
mkdir -p backups
chmod 700 backups
pg_dump --dbname="$DATABASE_URL" --format=custom --file=backups/edin.dump
chmod 600 backups/edin.dump
```

При восстановлении в **отдельную пустую базу** используйте `pg_restore --no-owner --no-privileges`, проверьте данные, затем переключите `DATABASE_URL`. Сохраняйте `JWT_SECRET` отдельно от базы. Автоматическое внешнее резервирование для бесплатного облачного варианта требует подключения вашего хранилища/расписания и без этих аккаунтов не настраивается.

## Обновление

1. Создать и проверить резервную копию.
2. Прогнать API-тесты и сборку фронтенда на новой версии.
3. Для изменения схемы выполнить подготовленную миграцию, протестированную на копии БД.
4. Обновить образ/Render deployment, сохранив `DATABASE_URL`, `JWT_SECRET` и тома.
5. Проверить health, вход, создание тестового заказа, SSE, историю.
6. При ошибке откатить образ; если менялась схема, действовать по проверенному плану миграции, не удалять данные.
